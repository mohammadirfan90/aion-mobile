# Technical spec

How the app is built. [CONTEXT.md](CONTEXT.md) explains *why*; this file explains *how*. Per-screen details are in
[SCREENS.md](SCREENS.md) and endpoint details in [API.md](API.md).

> **Expo changes every SDK.** Before using any Expo, Expo Router or React Native API, check the docs for the
> SDK version in `package.json` (see `AGENTS.md`). Always add packages with `npx expo install <pkg>`.

## 1. Stack

| Concern | Choice | Notes |
|---|---|---|
| Framework | Expo SDK 57, React Native 0.86, React 19, TypeScript strict | React Compiler and typed routes are on (`app.json`). |
| Navigation | `expo-router` (file-based) | Route groups `(auth)`, `(app)`, `(tabs)`. Auth gating with `Stack.Protected`. |
| Server state | `@tanstack/react-query` | Caching, refetch on focus, pull-to-refresh. Phase 3 adds persistence for offline use. |
| Client state | `zustand` | Only for session/auth state and settings (theme override, biometric lock). |
| Forms | `react-hook-form` + `zod` + `@hookform/resolvers` | One zod schema per form, in the feature folder. |
| Auth | `@supabase/supabase-js` with AsyncStorage session persistence | Follow the current Supabase "Expo React Native" quickstart for setup. |
| HTTP | `openapi-fetch` + types generated by `openapi-typescript` | `npm run api:types` generates `src/api/schema.d.ts` from `api/openapi.json`. |
| Streaming | `fetch` from `expo/fetch` | Only for `POST /ai/tutor-stream`. |
| Video | `expo-video` for MP4/HLS; `react-native-webview` for YouTube/Vimeo embeds | |
| Images | `expo-image` | |
| Icons | `lucide-react-native` | `react-native-svg` is already installed. |
| Font | Geist (via `expo-font`; package `@expo-google-fonts/geist` if available, otherwise bundle the font files) | Fall back to the system font if loading fails. |
| Markdown | A maintained React Native markdown renderer (e.g. `react-native-marked`) | Record the choice as a decision in CONTEXT.md. |
| Pickers | `expo-image-picker`, `expo-document-picker`, `expo-image-manipulator` | Avatar, forum image, assignment file. Convert photos to JPEG and resize them before upload (the API rejects HEIC). |
| Native extras (Phase 3) | `expo-camera` (QR), `expo-local-authentication`, `expo-haptics`, `expo-sharing`, `expo-web-browser` | |
| Builds | EAS Build (APK for submission) | Phase 4. |

Don't add a library outside this table without writing a decision in CONTEXT.md first.

## 2. Folder structure

```
api/

src/
  app/                      # ROUTES ONLY (Expo Router). Each file is thin: it renders a screen component.
    _layout.tsx             # providers + root Stack with Stack.Protected guards
    (auth)/_layout.tsx
    (auth)/welcome.tsx  login.tsx  signup.tsx  verify-email.tsx  forgot-password.tsx  reset-password.tsx
    (app)/_layout.tsx       # Stack for signed-in area
    (app)/(tabs)/_layout.tsx
    (app)/(tabs)/index.tsx  explore.tsx  learning.tsx  community.tsx  profile.tsx
    (app)/course/[id]/index.tsx  curriculum.tsx  certificate.tsx
    (app)/lesson/[id]/index.tsx  notes.tsx  summary.tsx  comments.tsx  quiz.tsx  assignment.tsx
    (app)/tutor.tsx
    (app)/forum/[id].tsx  new.tsx
    (app)/support/index.tsx  [id].tsx  new.tsx
    (app)/profile/edit.tsx
    (app)/settings.tsx
    verify/index.tsx  [code].tsx      # public: certificate verification (scan or type a code)
  features/                 # one folder per area; screens, feature components, hooks, schemas
    auth/  home/  catalog/  learning/  lesson/  quiz/  assignment/  tutor/
    community/  support/  profile/  certificate/
      screens/<ScreenName>.tsx
      components/
      hooks.ts              # react-query hooks; the ONLY way screens get data
      api.ts                # calls the API (real) or returns fixtures (mock)
      schemas.ts            # zod form schemas
  api/
    client.ts               # openapi-fetch client, auth header, envelope unwrap, ApiError
    schema.d.ts             # GENERATED. Never edit by hand.
    types.ts                # hand-written types for endpoints the spec leaves untyped (from API.md)
    query-keys.ts
  mocks/
    fixtures/               # typed fake data, one file per area
    delay.ts                # small artificial latency so loading states are visible
  lib/
    env.ts                  # reads and validates EXPO_PUBLIC_* vars
    supabase.ts
    auth-store.ts           # zustand: session, user, status
    format.ts               # dates, durations, prices
    course.ts               # effective price + access mode (API §3)
    lesson.ts               # normalize lesson metadata, pick the renderer, parse dynamic_page blocks (API §4)
    sse.ts                  # AI tutor stream parser (API §13)
  components/ui/            # shared UI kit (see §7)
  theme/
    tokens.ts  index.ts     # colors, spacing, radius, typography; useTheme()
```

Rules:
- `src/app/*` files only import and render a screen from `src/features/**/screens`. No logic in routes.
- Features may import from `components/ui`, `lib`, `api` and `theme`. They don't import from another feature. If
  two features need the same thing, move it to `components/` or `lib/`.
- File names are `kebab-case.ts(x)` except screen and component files, which are `PascalCase.tsx`.
  Hooks are named `useX`.
- Use the `@/` import alias (it maps to `src/`).

## 3. Environment

`.env` (not committed) and `.env.example` (committed):

```
EXPO_PUBLIC_API_URL=https://<api-host>          # without /api/v1
EXPO_PUBLIC_SUPABASE_URL=https://<project>.supabase.co
EXPO_PUBLIC_SUPABASE_ANON_KEY=<anon key>

```

`src/lib/env.ts` validates these with zod at startup. If mocks are off and a value is missing, show a clear error
screen instead of crashing.

## 4. Data layer

Screens never call `fetch`. The chain is always **screen → hook → feature api → client or fixture**.

```ts
// features/catalog/api.ts
export async function listCourses(params: CourseListParams): Promise<Course[]> {
  if (env.useMocks) return mockDelay(fixtures.courses.filter(...));
  return unwrap(await api.GET('/api/v1/courses', { params: { query: params } }));
}

// features/catalog/hooks.ts
export function useCourses(params: CourseListParams) {
  return useQuery({ queryKey: qk.courses.list(params), queryFn: () => listCourses(params) });
}
```

- **Envelope.** The API returns `{ success: true, data }` or `{ success: false, error: { code, message } }`.
  `unwrap()` in `api/client.ts` returns `data` or throws `ApiError { code, message, status }`.
- **Auth header.** `api/client.ts` has middleware that reads the current Supabase session and sets
  `Authorization: Bearer <access_token>`. On a 401 it tries one `supabase.auth.refreshSession()` and retries once.
  If that fails, it signs out.
- **Query keys** all live in `api/query-keys.ts`, so cache invalidation is in one place.
- **Mutations** invalidate the affected keys. Optimistic updates are used for upvotes, notes and lesson-complete.
- **Loose JSON fields.** `learnings`, `tags`, `pricingConfig`, `accessConfig` and lesson `metadata` arrive as JSON
  objects or arrays, but can be `null` or have missing keys. Normalize them **once**, inside the feature `api.ts`,
  into strict app types with safe defaults. Course price and access logic live in `lib/course.ts` (API §3);
  lesson renderer selection lives in `lib/lesson.ts` (API §4).
- **Mocks.** Fixtures must have the same shapes the real API returns (after parsing), typed with
  `api/types.ts` or the generated schema. Include edge cases: empty lists, long titles, missing thumbnails, a
  locked chapter, and every lesson type. Mock mutations update an in-memory copy so the UI behaves realistically.
- **Errors.** Map `ApiError.code` to friendly text in one helper (`lib/errors.ts`). Show `RATE_LIMITED`,
  `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `NOT_ENROLLED` and network failures distinctly. `unwrap()` must
  survive non-JSON error bodies and map any 429 to `RATE_LIMITED` (API §1).

## 5. Auth and session

```
App start ──► restore Supabase session from AsyncStorage
   │                 │
   │   no session ───┴──► (auth) group: welcome → login / signup
   │   session ─────────► GET /users/me ──► (app) group, user stored in auth-store
   │
Login:        supabase.auth.signInWithPassword({ email, password })
Signup:       POST /auth/signup {firstName,lastName,username,email,password}
              with header X-Aion-Client: mobile                                 → verify-email screen
Verify email: supabase.auth.verifyOtp({ email, token, type: 'email' })         (needs B-02)
Forgot:       supabase.auth.resetPasswordForEmail(email)                        → reset-password screen
Reset:        supabase.auth.verifyOtp({ email, token, type: 'recovery' }) → supabase.auth.updateUser({ password })
Logout:       supabase.auth.signOut() + queryClient.clear()
```

- `auth-store` exposes `status: 'loading' | 'signedOut' | 'signedIn'`, `user` (from `/users/me`) and `session`.
- The root layout keeps the splash screen up while `status === 'loading'`, then uses `Stack.Protected` to show
  either the `(auth)` or the `(app)` group.
- In mock mode, any email and password signs in as a fixture student. A dev-only switch on the Settings screen
  can swap to a fixture admin.
- Supabase's `autoRefreshToken` should only run while the app is in the foreground (use `AppState`, as the
  Supabase Expo guide shows).

## 6. Design system

The tokens match the web app's neutral theme. Define them in `src/theme/tokens.ts` and read them only through
`useTheme()`. **No hex values inside screens.**

| Token | Light | Dark |
|---|---|---|
| `background` | `#FFFFFF` | `#0A0A0A` |
| `foreground` (text) | `#0A0A0A` | `#FAFAFA` |
| `card` | `#FFFFFF` | `#171717` |
| `muted` (subtle surfaces) | `#F5F5F5` | `#262626` |
| `mutedForeground` (secondary text) | `#737373` | `#A1A1A1` |
| `border` | `#E5E5E5` | `rgba(255,255,255,0.10)` |
| `primary` (buttons, active) | `#171717` | `#E5E5E5` |
| `primaryForeground` | `#FAFAFA` | `#171717` |
| `destructive` | `#E7000B` | `#FF6467` |
| `success` | `#16A34A` | `#4ADE80` |
| `warning` | `#D97706` | `#FBBF24` |
| `ring` (focus) | `#A1A1A1` | `#737373` |

- **Radius:** `sm 6`, `md 8`, `lg 10` (default), `xl 14`, `full 999`.
- **Spacing:** a 4-point scale: `1=4, 2=8, 3=12, 4=16, 5=20, 6=24, 8=32, 10=40, 12=48`. Screen side padding is 16.
- **Type (Geist):** `display 28/34 bold`, `title 22/28 semibold`, `heading 18/24 semibold`, `body 15/22 regular`,
  `bodyStrong 15/22 semibold`, `caption 13/18 regular`, `label 13/18 medium`, `tiny 11/14 medium`.
  The body text minimum is 13.
- **Touch targets** are at least 44×44.
- **Theme:** follow the system by default; Settings can force light or dark.
- **Motion:** use Reanimated for small transitions only (200–250 ms). Respect the OS "reduce motion" setting.
- The existing `src/components/auth-screen.tsx` is the visual reference for the pill inputs and dark pill buttons;
  restyle it onto these tokens.

## 7. Shared UI kit (`src/components/ui`)

These are built in Phase 0, before any screen. Each takes theme tokens, supports dark mode, and has
accessibility labels.

`Screen` (safe area, optional scroll, pull-to-refresh, keyboard avoiding) · `Text` (variants from §6) ·
`Button` (primary / secondary / ghost / destructive; loading; icon) · `IconButton` · `TextField` (label, error,
secure toggle, `autoComplete`, `textContentType`) · `OtpInput` (6 boxes, paste support, backspace moves back) ·
`Card` · `ListItem` · `Avatar` (image or initials) · `Badge` · `Chip` / `ChipGroup` · `SegmentedControl` ·
`ProgressBar` · `ProgressRing` · `Skeleton` · `EmptyState` · `ErrorState` (with retry) · `Divider` ·
`SearchBar` · `Toast` (simple: success / error / info) · `Header` (title, back, actions).

Every data screen must handle four states: **loading** (skeletons, not spinners, for lists), **empty**,
**error** (with retry) and **content**.

## 9. Quality gates (Definition of Done)

A task is only `done` in [TRACKER.md](TRACKER.md) when:

1. `node scripts/verify.mjs check` passes. It runs `npm run check` (`expo lint` and `tsc --noEmit`, set up in
   Phase 0), the tests, the public-repo hygiene scan, and the code rules below where they can be automated.
   A finished phase must also pass `node scripts/verify.mjs phase <n>`.
2. The screen or feature works in mock mode on Android (emulator or device). Check iOS too if someone has access.
3. It looks right in **light and dark** mode and on a **small phone (360×640)**.
4. Loading, empty and error states exist where data is involved.
5. No hard-coded colors, no `any` without a comment explaining why, and no `console.log` left behind.
6. The tracker row is updated and a log entry is written.

Unit tests (`jest-expo`) are required only for `lib/` helpers: `course.ts`, `lesson.ts`, `sse.ts`, formatting
and error mapping.
Screens are checked by hand against the acceptance list in SCREENS.md.

## 10. Git workflow

- `main` must always build. Work on a branch per task or small group of tasks:
  `irfan/p1-s07-home`, `maria/p1-s02-login`.
- Open a pull request into `main`. The other person reviews it (a short look is fine), then merge.
- Commit messages are one line: `<task-id>: <what changed>`, for example `P1-S07: home screen with mock data`.
- Never commit `.env`, `ios/` or `android/` (they are generated), or `node_modules`.
